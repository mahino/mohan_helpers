Storage Questions – English Version
Background
The customer observed that Recovery Points usage in Prism Element storage details is high, especially in one environment compared to another, and asked:

What can be deleted to reduce Recovery Points usage?
What is the impact/effect of enabling deduplication on a storage container?
If deduplication is enabled, can it be disabled later?
1) What contributes to Recovery Points usage
Recovery Points usage can include multiple data types, not just one snapshot category:

VM-level Acropolis snapshots
Protection Domain (PD)-based snapshots (local/remote)
Prism Central recovery points (policy/manual)
Third-party backup snapshots (for example, names with third_party_backup_snapshot_)
Images/ISOs and clone-related storage usage
Deletion candidates to reduce usage
You can reduce usage by deleting unneeded items such as:

old PD snapshots
old Prism Central recovery points
expired/orphan third-party backup snapshots (after validating ownership/retention)
Always confirm retention requirements and restore requirements before deletion.

2) How to check Recovery Point breakdown
Recommended (most accurate)
Use ss_exclusive_usage.py to check exclusive/reclaimable usage per recovery point/entity.

UI-based (easiest to view)
Use Prism Central:

Data Protection → VM Recovery Points
Check reclaimable space and per-item details
CLI alternatives (useful, but less precise for reclaimable space)
Use ncli to inspect:

PD list
PD snapshots
Entity-centric PD/snapshot details
ncli gives useful size indicators (for example Snapshot Size), but does not always equal exact reclaimable space shown by dedicated tooling/UI calculations.

3) Deduplication impact on storage containers
Benefits
Can reduce physical storage usage significantly where duplicate blocks are common (for example, full clones, similar datasets).
Considerations / risks
CVM resource requirements (memory and metadata overhead considerations)
Possible replication performance impact in some DR/protection scenarios
Workload suitability matters; some clone workflows may not gain meaningful additional benefit
4) Can deduplication be turned off later?
Yes, deduplication can be disabled later.

Important behavior:

Disabling dedupe affects new writes going forward
Existing already-deduplicated data is not automatically “un-deduped”
To fully return data to non-deduped placement behavior, data migration to a non-dedup container may be required
5) “Data Disk Space Usage High” capacity validation
For disk-space-high alert risk evaluation, do not rely only on total cluster capacity.

Check per-disk usage in Prism Element:

Hardware → Table → Disk
Look for imbalanced/high individual disks approaching threshold
This is the correct operational way to assess alert risk.

6) Cases where UI does not show expected recovery points
There can be cases where Prism Central UI does not visibly map certain recovery-point remnants (for example, if related VM objects are no longer present, third-party artifacts, or stale internal mappings).

In such situations:

validate via CVM CLI (ncli PD/snapshot inspection)
then remove only verified stale/unneeded objects with care
Practical Recommendation
Use this order:

Prism Central UI for quick visibility and reclaim candidates
ss_exclusive_usage.py for precise reclaimable usage
ncli for backend validation and mapping gaps
Delete only after retention/ownership confirmation
For disk-high alerts, always check per-disk usage in PE Hardware view
